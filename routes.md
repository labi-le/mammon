# routes — :app module reference

> **When to read this:** for orientation before any change, and after adding, removing,
> or restructuring a package or changing its public surface — update this file in the
> same change.

Module `:app` is the only Gradle module. Package root: `app.mammon`.
Config: `applicationId app.mammon`, minSdk 26, compile/target SDK 35.

## As it exists

### Kotlin (`app/src/main/kotlin/app/mammon/`)

| File | Contents |
|---|---|
| `MainActivity.kt` | Two-card UI (SAF config + root mount), classic Views over `R.layout.activity_main`; saves `Prefs`, probes the share, fires ACTION_VIEW on the provider root, drives Mount/Unmount and Install-module off the main thread. Save validates every field and writes nothing when any one of them is in error, so a rejected uid or port cannot be silently coerced. Mount hands `RootMount` a `FuseLaunch` built from `applicationInfo.sourceDir`, a log path under `cacheDir` and the saved `AuthIdentity`. The mountpoint field error comes from `MountpointPolicy.refusalFor`, called by `mountpointFieldError` (`MainActivity.kt:351-360`) and from no private rule of its own — true only since the absoluteness `if` that used to sit in `onMount` was deleted into that composition. `RootMount.resolveTarget` calls the same one, so the card refuses only what a path alone can earn — the shared-storage tree root, a name under `Android/`, a non-emulated path in Android's own storage, a `.` or `..` component, a spelling that is not absolute as saved, and a bare `/` — and no other entrance can mount what the field rejected. The last two share `err_bad_mountpoint_absolute`, whose text already names both. `NO_SHARED_PEER` is deliberately not a field error, because whether THIS device's shared storage can carry a visible mount needs root and therefore arrives later as a `MountDiagnosis`. The status line names the backing that landed and, for a routed mount, the path the user can open rather than the master path the mount was made at. The activity also owns the window chrome that targetSdk 35 hands back to the app: `applyEdgeToEdgeInsets` pads the app bar and the scroller out of the system bars and gives the scroller a bottom margin for the keyboard — a margin, not padding, because `NestedScrollView` measures scroll-into-view against `getHeight()` and ignores its own padding — and `applyBarIconAppearance` sets the bar icon polarity from the night bit, which `themes.xml` cannot do without forking across `values-night` and `values-v27`. |
| `ModuleInstall.kt` | The Install-module decision core, Android-free: the su probe script (one line per source, `modules_update/mammon_fsloader` before `modules/mammon_fsloader`), the verdict mapping over `Probe.PRESENT`/`ABSENT`/`OUTDATED`/`UNAVAILABLE` (an install at or past the bundled versionCode is PRESENT; an older one is OUTDATED and stages the newer zip; a denied, timed-out or unparseable probe is UNAVAILABLE, never silently absent and never silently up to date), `bundledVersionCode` reading `module.prop` out of the packaged asset zip so that number has one home, and the staged-file policy (`cacheDir/mammon-module.zip`, truncated on every press). The zip itself is packed at build time by `packModuleZip` in `app/build.gradle.kts` and rides as an APK asset; installing happens in Magisk after a chooser hand-off, which mammon cannot observe. |
| `Prefs.kt` | SharedPreferences: host, export, port (default 2049), AUTH_SYS identity, last mountpoint; `spec()` re-parses into an `ExportSpec` and `target()` pairs it with the identity as an `NfsTarget`. |
| `ExportSpec.kt` | Parses "host[:port]:/export"; IPv6 literals bracketed; port range and traversal rejected. Location only — the claimed account lives in `AuthIdentity`. |
| `AuthIdentity.kt` | The AUTH_SYS identity as a triple (uid, gid, supplementary gids) with the one parser for its `uid:gid:aux,aux` form, shared by `Prefs` and the FUSE daemon's argv. uid and gid are `unsigned int` on the wire, so the accepted range is 0…4294967295; the list is capped at the `gids<16>` of RFC 5531 appendix A. `DEFAULT` is a starting point, not a fact: root_squash maps uid 0 to nobody, and the owning account differs per server. |
| `PathCodec.kt` | documentId <-> export-absolute path; rejects "..", empty segments, leading/trailing slashes. `componentOf` is the single guard between a foreign display name and one wire component (no separator, no NUL, no dot name), and `childPath`, `childDocId` and `parentOf` all delegate to it or to `pathFor` — so an id split into parent + name for a mutation is validated here, not left to the backend. Every provider id passes through this file. |
| `NfsSession.kt` | The contract the provider and the FUSE daemon share: reads (`probeRoot`/`stat`/`list`/`openFile`) plus the mutating half (`createFile`/`makeDirectory`/`remove`/`setAttributes` keyed by parent + name, and `NfsFile.writeAt`), every one of them abstract, `NfsFile.writeAt` included, so a backend that declares `implementsWrites` cannot leave one out and fail at runtime instead — the seam's only default body is `streamFor`, a sequential adapter over `openFile`; `implementsWrites` names what the BACKEND implements, never what the export or the identity permits; `remove` carries an optional `isDirectory` hint — the type the caller already holds, null meaning "find out", and TRUSTED rather than verified, so it may be supplied only where the type is authoritative: a wrong one costs the refused round trip before the lookup the hintless path pays anyway, and on a server that honours REMOVE on a directory (RFC 1813 §3.3.12 permits it) the mismatched procedure succeeds instead, which no later step corrects — a hint the v4.1 backend ignores, one REMOVE serving both types there, and the v3 backend spends on picking REMOVE or RMDIR without a lookup of its own; the FUSE opcode supplies it (`FuseNfsDaemon.kt:477-481`), while SAF is handed a documentId alone and passes null (`NfsDocumentsProvider.kt:232`). `NfsFailure` is the sealed refusal set — `PermissionDenied`, `NotFound`, `AlreadyExists`, `DirectoryNotEmpty`, `OutOfSpace`, `Unsupported`, `Timeout`, `Unreachable`, `Server` — that both frontends map without reading a message; the last two are the transport's, and the connection parts them rather than the request: `Timeout` has two producers and the connection still standing behind both — a call that outran its deadline, and an NFS3ERR_JUKEBOX the v3 backend maps here rather than waiting out — so whether the server applied it is unknown and a re-send could run it twice, while `Unreachable` is a connection that will not carry this call's answer — a server out of reach, a rebuild that failed or was refused, or a loss on an operation a rebuild may not re-send — so the call ends without one whether or not the server ever saw it. Both frontends spend that distinction on the message a user reads and nowhere else: `Fuse.EIO` for both (`FuseNfsDaemon.kt:545-546`), `SafErrno.IO` and `FileNotFoundException` for both (`SafContract.kt:151-152`, `:170-171`), two different strings only in `NfsDocumentsProvider.kt:493-494`. `Unsupported` does not mean the app cannot do it: it means the operation is not available here, and the common case is now a server refusing a procedure the specification lets it refuse — RFC 1813 §3.3.13 lists `NFS3ERR_NOTSUPP` for RMDIR, and NFS4ERR_NOTSUPP lands on the same case, so this is not v3's condition alone. Also `NodeAttrs`/`ChildEntry`, `NfsTarget`, `NFS_READ_CHUNK`/`NFS_WRITE_CHUNK`, the shared directories-first ordering, and `NfsSessions.select` — v4.1 first, v3 on failure, the v4 error kept as a suppressed exception. `NfsFile.readAt` is the positional read FUSE needs; `streamFor` is a default adapter over it. |
| `NfsAccess.kt` | The NFSv3 `NfsSession` over `com.emc.ecs:nfs-client`, reads and writes both — stat, list, positional READ, and the mutating half: `createFile` (one GUARDED CREATE, so a name already taken comes back NFS3ERR_EXIST instead of truncating, and the reply's own handle and attributes spare it a LOOKUP), `makeDirectory` (mode 0755, as the v4.1 backend sends), `remove` (NFSv3 splits the seam's one removal, so the entry's type picks REMOVE or RMDIR — the caller's `isDirectory` when it has one, a LOOKUP when it does not — and a REFUSED call is re-decided by re-reading the type, not by the status, since unfs3 answers RMDIR on a file with NFS3ERR_STALE and deletes a directory with REMOVE — a success is re-decided by nothing, so a wrong hint a server honours stands; the other call goes out only once the fresh type contradicts the one tried, and not at all after a `POLICY_REFUSALS` status — ACCES, PERM, ROFS, NOTEMPTY — which the other call would be refused with too, where sending it could only reach an object that took the name since), `setAttributes` (SETATTR's post-operation attributes are the read-back) and `Handle.writeAt` (chunked here against FSINFO `wtmax` clamped by `NFS_WRITE_CHUNK`, cached including the fallback, every WRITE `FILE_SYNC`, so this backend owes no COMMIT and no write-verifier restart). CREATE, MKDIR, REMOVE and RMDIR go out through the library's NAKED one-shot calls, status checked here, because the wrapped ones re-send on any `RpcStatus.NETWORK_ERROR` without asking whether the operation is idempotent and v3 has no session slot and no replay cache to catch the duplicate: a lost mutation is reported failed rather than performed twice. READ, GETATTR, SETATTR and WRITE keep the retrying path, being positional and idempotent. Listing is one READDIRPLUS cookie loop carrying child attributes (symlinks and special files are not listed; an entry whose attributes the server withheld costs one LOOKUP instead of being dropped), latched for the session to READDIR plus a LOOKUP per child on NFS3ERR_NOTSUPP, since RFC 1813 makes READDIRPLUS optional and real servers refuse it. Every READ and every listing page is capped by `UNFRAGMENTED_REPLY_MAX` (61440) so no reply spans two RPC record fragments: `RecordMarkingUtil.removeRecordMarking` advances its cursor by the fragment size and not by header-plus-size, so the library misreads any record the server split, and libtirpc and ntirpc close a fragment every 65532 bytes of payload. A large READ therefore comes back short, which every caller already loops over; the write direction needs no cap, the library's own record marking being correct. Everything works from filehandles rather than the library's `Nfs3File`, which pays a GETATTR per component and answers null whatever went wrong; `walk` takes the prefixes it can from the handle cache, spends a LOOKUP on each one it cannot and always on the leaf, whose off-the-wire attributes its callers came for, and keeps the reason. Resolved handles live on the session in `HandleCache`, access-ordered, capped at `MAX_ENTRIES` (256) and keyed by export-absolute path, so only the first operation in a directory pays the full walk; an entry answers absent once `TTL_NANOS` (5 s, the entry TTL the FUSE layer already advertises) has passed on its monotonic stamp, which is correctness rather than tuning — a handle survives a foreign rename, staying valid while it stops denoting its own key, so no status can expose the stale binding and only the clock retires it, leaving that window as the residual; `forgetTree` drops a path together with its subtree when the server answers NFS3ERR_STALE or NFS3ERR_BADHANDLE and after a `remove` that took a directory, `forget` drops the path alone after one that took a file, and `handleOf` re-resolves a rejected cached prefix once — safe even ahead of a mutation, since resolution is pure LOOKUP and nothing destructive has gone out yet. Every wire call goes through `failing`, so no frontend classifies a failure by matching substrings of a message: `failureFor` maps an RFC 1813 status onto the table `NfsV4Access` applies to NFSv4 statuses, plus the one row v4.1 has no use for — JUKEBOX -> `Timeout`, NOTSUPP -> `Unsupported` now being a row on both sides — because this backend does not wait out a JUKEBOX the way `NfsV4Access` retries NFS4ERR_DELAY, and the transport's `RpcException` is dug out of the cause chain — the library buries it under an NfsException wearing NFS3ERR_IO — with its message read for the `Timeout` / `Unreachable` split, which is why `TransportLoss` cannot answer for this backend. AUTH_SYS via `CredentialUnix` built from the `AuthIdentity`, matching `NfsV4Access`: under AUTH_NONE a stock Linux server accepts the MOUNT and then refuses GETATTR with NFS3ERR_ACCES. One long-lived session per target; the provider rebuilds it when the config or the identity changes. |
| `NfsV4Access.kt` | The NFSv4.1 `NfsSession` over `org.dcache:nfs4j-core` XDR + `org.dcache:oncrpc4j-core` RPC: EXCHANGE_ID/CREATE_SESSION/RECLAIM_COMPLETE handshake with hand-built channel attributes, one COMPOUND per operation (SEQUENCE + PUTFH + LOOKUPs + op + hand-built tail), READ/WRITE/SETATTR on the anonymous stateid, AUTH_SYS via the local `AuthSys` credential, and two recoveries rather than one: a session re-established in place on a status the server returned, and — when the connection is gone instead of answering, which `TransportLoss` decides — a whole transport rebuilt, new client, new session, cached root handle cleared. The rebuild runs both before a COMPOUND whose socket is already closed, where nothing has reached the wire, and after one that died in flight, where creates, MKDIR and REMOVE are never re-sent by it: a lost mutation is reported failed rather than risked twice. Creation is the only operation taking OPEN state: `OPEN(OPEN4_CREATE, GUARDED4)` + GETFH + CLOSE in one COMPOUND, with the CLOSE retried alone (and the fused form abandoned for the instance) on a server that refuses it there. READ and WRITE payloads come from `grantedChunk`, which honours what CREATE_SESSION granted rather than an app constant. `recoverable` narrows retries for an operation that must not run twice; `sa_cachethis` stays false because every attempt takes a fresh slot and sequence ID. `Fattr4Codec` decodes the three requested attributes and encodes the SETATTR and create attributes. |
| `TransportLoss.kt` | The pure decision `NfsV4Access`'s recovery turns on: "the connection is gone" versus "the server answered". The cause chain is walked from the top and the first of the two kinds met decides: an `EOFException`, `ClosedChannelException` or `SocketException` is loss, but an NFS status above one of them wins and is not, because the connection carried the request and the reply both — a socket error nested under a status is therefore not loss. Neither is the `nfs4 call timed out` wrapper — a timeout cannot say whether the request ever reached the server, so re-sending on one is how a create runs twice. The walk is depth-capped and tolerates a cause that points at itself. `mayResend` is idempotence and nothing more. Android-free and unit-tested, following the `MountpointPolicy` convention. |
| `NfsDocumentsProvider.kt` | SAF root for the configured export, readable, and writable over either protocol version where the server permits it; `withTimeout(NFS_TIMEOUT_MS)` (15 s) wraps a BLOCKING body, so it bounds the suspension and not the work — neither a socket read nor monitor-enter is a cancellation point, so it is no hard ceiling on a call already on the wire; the real bounds are the backend's per-COMPOUND deadline (also 15 s), paid per round trip and so O(path depth) for one attempt, and its per-`resilient` recovery budget, which a SAF call that pages or chunks arms afresh for each page and each chunk; one long-lived session per `NfsTarget` (`nfsInstance`, which also caches the chosen protocol version). Reads stream through a reliable pipe with a 64 MiB cap; writes go through `StorageManager.openProxyFileDescriptor` on a fixed set of four looper threads, so a server refusal becomes an errno on the client's own `write(2)` instead of a lost write after its fd is gone. `createDocument` de-duplicates a colliding name by retry rather than throwing (a guarded create — GUARDED4 on v4.1, `NfsCreateMode.GUARDED` on v3 — makes the server the arbiter), `deleteDocument` is non-recursive, mode `w` truncates and `wa` is refused, and each mutation notifies the PARENT's child-documents URI — which the returned cursors register via `setNotificationUri`, without which no refresh reaches anyone. |
| `SafContract.kt` | The SAF decisions that need no round trip and no Android runtime, split out because a JVM unit test can invoke no member of a `DocumentsProvider`: `SafFlags` (which `FLAG_*` each row kind carries, optimistic and gated only on `implementsWrites`), `SafOpenMode` (the mode strings served, and the `w`-truncates / `wa`-refused rulings), `SafNaming` (the one ext<->MIME table, its derived first-wins inverse, the extension a create owns and the ` (2)` retry name), and the `NfsFailure` mappings — `asSafException` onto `FileNotFoundException` for every case, the one refusal the system UI renders and the one the write methods declare, and `safErrno` onto a named errno, named because `OsConstants` is filled by native init and reads zero off-device; `Unsupported` answers `ENOSYS` there, since both backends write and `EROFS` would be a false statement about the filesystem. `proxyOpenOutcome` classifies a failed `openProxyFileDescriptor` instead: an `IOException` stays a file error, the `IllegalStateException` a device that cannot mount the framework's proxy bridge raises becomes one too (carrying the original as its cause), and everything else — a bug of ours in that open path included — keeps its type, so a bug never reads as a file error. |
| `NfsScanner.kt` | Discovery: expands the current IPv4 subnet into candidates (`addresses`, capped to the baseIp's /24, network+broadcast excluded) and probes TCP 2049 in parallel (`scan`); `currentSubnet` reads the active network's IPv4 LinkAddress. |
| `MountsParser.kt` / `RootMount.kt` | `/proc/mounts` line parser (plus the octal `unescape` that `EmulatedMount` reuses on mountinfo); one Mount button behind a three-rung ladder driven through `su --mount-master -c` (nsenter fallback): kernel `vers=4.2`, kernel `vers=3`, then the FUSE daemon. Ahead of the ladder sits one routing decision (`resolveTarget`): a mountpoint inside shared storage is redirected to the propagation master `EmulatedMount` derives, which needs the GLOBAL namespace's propagation state, so `cat /proc/1/mountinfo` runs through the same su path before any mount — an unreadable table is `NO_ROOT` or `GENERIC`, never a guessed route. A routed mount then creates the LOWER directory `/data/media/<u>/<name>` instead of its mountpoint, because a `mkdir` through the fuse view would take MediaProvider's own 0775 ownership and need that daemon running, while a directory created in the lower tree is answered by the view's next LOOKUP straight from `lstat(2)` — no scan, no wait. Each rung best-effort `modprobe`s its filesystem modules first, since Android kernels usually ship nfs/fuse as modules `/proc/filesystems` does not list until loaded. State and the reported fs type come from /proc/1/mounts so the check matches the global namespace the mount landed in, and `nfs`, `nfs4` and `fuse` all count as mounted — the `/proc/filesystems` lookup keeps its own set so a FUSE-only kernel never looks NFS-capable. For a routed mount that check is made at the app-visible path, because that is the claim made to the user: mounted at the master and absent from the view means the kernel never replicated it, so `mounted` tears the master-side mount down through the same su ladder that made it and reports `EMULATED_NOT_PROPAGATED` (`mounted`, `RootMount.kt:239-264`) — no screen names the master path, so a mount left standing there is the one nobody goes back for. A teardown that itself failed reports `EMULATED_NOT_PROPAGATED_STUCK` instead, with the message that admits it and names the Unmount button, since "removed it again" is a claim and not an outcome. An unreadable `/proc/1/mounts` stays UNKNOWN and attempts no teardown at all. Unmount runs at the master path for the same propagation reason — a slave never propagates to its master, so a `umount` inside the `/storage` view would leave the real mount up. When the routing read cannot get a `su` at all it stops there and returns that `NO_ROOT` verdict instead of spending a second spawn that cannot succeed either, since each one can block for `SU_TIMEOUT_SECONDS` with both buttons disabled; every other refusal still falls back to the literal path, because those are answers about the path alone, decided before any `su` has run, and the mount they name may still be standing from another entrance (`unmount`, `RootMount.kt:508-514`). `Result.appVisible` is non-null only for a routed mount, which is how the UI knows the two paths differ. A ladder that runs out is classified by `classifyMountFailure` (`RootMount.kt:443-467`) into the five verdicts that function can return — `NO_ROOT`, `KERNEL_LACKS_FUSE`, `MODULE_FILES_PRESENT`, `FUSE_DAEMON_FAILED`, `GENERIC` — from the exit code, stderr, a root-context `/proc/filesystems` dump split off the same su output (a blank list is no evidence — every inferred kernel claim needs actual text, so an unreadable read degrades to `GENERIC`, never to `KERNEL_LACKS_FUSE`; only the observed missing `/dev/fuse` keeps its unconditional verdict), an `ls | grep` over `/vendor/lib/modules` and `/system/lib/modules` (module file present but nothing registered ⇒ `MODULE_FILES_PRESENT`) and the daemon's own log line. The enum's three emulated members reach a caller from nowhere near that function: `EMULATED_NO_SHARED_PEER` is `resolveTarget`'s answer, given before the first rung runs, and `EMULATED_NOT_PROPAGATED` / `EMULATED_NOT_PROPAGATED_STUCK` are `mounted`'s, given on a rung that already exited 0 — so no exhausted ladder can produce them, and reading the enum as one ladder verdict set hides where three of its eight members are decided (`MountDiagnosis`, `RootMount.kt:50-68`, is the whole set). `MainActivity.mountFailureText` (`MainActivity.kt:302-316`) maps all eight plus null to a string resource. `MountpointPolicy` (a sibling internal object) survives with a narrowed job, and `refusalFor` (`RootMount.kt:718-732`) is the one spelling of it: it crosses `EmulatedMount.localRefusal` with `isInStorageSurface`, so `/storage` itself (tmpfs), `/sdcard` outside the emulated tree and `/data/media` (which sits BELOW the fuse daemon rather than in the propagating view) still earn a refusal, while a path inside emulated storage is routed instead. That same non-emulated arm is the one whose target is the saved string itself, so it also refuses what root could not use as a mountpoint: `NOT_ABSOLUTE` for a spelling that is not absolute AS SAVED — `" /mnt/nas"` was a root `mkdir -p` of a relative path, since `normalize` decides and never rewrites — and `IS_FILESYSTEM_ROOT` for one that normalizes to `/`. A routed path is exempt because its target is derived from the normalized request, which is exactly where `fslib.sh` re-asks the same question of the same saved string. Being a pure function both entrances call — the mountpoint field and `resolveTarget` (`RootMount.kt:168-169`) — rather than a private method of the activity is the point: while the rule lived in the activity, `RootMount.mount("/data/media/0/nfs")` walked straight past it. `fslib.sh`'s automount carries the same routing and the same refusals, down to the `/mnt/user/<u>/emulated` spelling `MASTER_SPELLING` anchors on `\d+`: a shell glob's `*` spans slashes, so the module pins that `<u>` to digits itself rather than let `/mnt/user/x/y/emulated/0/nfs` route where the app mounts it literally. |
| `EmulatedMount.kt` | The routing rule for shared storage, pure and Android-free — mountinfo text and a path in, a verdict out — so the decision is testable with no device. `/storage/emulated` is a SLAVE of its propagation peer group: it receives mounts and never sends them, so a mount made there stays in the namespace that made it and reaches no app. The same fuse device is also mounted at that group's shared MASTER (`/mnt/user/<u>/emulated` on a stock tree), and a mount made there is replicated by the kernel into every slave — which is how vold's own `Android/data` and `Android/obb` mounts appear INSIDE the emulated tree, the standing precedent against "emulated storage cannot carry a mount". So `route` answers with three paths at once: the master path to mount at, the `/data/media/<u>/<name>` lower directory that must exist first, and the `/storage/emulated/<u>/<name>` the user is told about. The master is derived per device and never hardcoded, because it varies by OEM, by user profile and by release: the fuse line at the emulated view is taken last-wins (a later mount at one point is what is visible there now), and a peer is accepted on peer-group identity, which already proves the two entries are one fs instance without a device-number check on top. The `propagate_from:` group is tried FIRST and `master:` only as a fallback, never as one set — `master:` is the immediate master's group id, which `fs/pnode.c get_dominating_id` may leave with no line under the reading root at all, while `propagate_from:` is the nearest REACHABLE master group, so keying on `master:` alone would report no route on a device where the route works; trying them in that order also keeps mountinfo line order from deciding, and within a group the FIRST candidate wins (`mountSite`, `EmulatedMount.kt:149-157`). Mountinfo's optional tags are a zero-to-four variable-length list, so every field past them is located by searching forward for the literal `-` separator rather than by counting columns, and a mount point is unescaped before comparison because ours are user-typed. A view carrying a bare `shared:` and neither tag above it needs no master at all: it sends propagation itself, so the mount is made where it stands and `mountAt` equals `appVisible` (`mountSite`, `EmulatedMount.kt:161-163`). Trying there rather than refusing is deliberate and asymmetric — `RootMount` verifies the mount at the app-visible path and withdraws it when it did not propagate, so a wrong attempt corrects itself, while a refusal is terminal and denies a device the route works on. A line carrying `shared:N` AND `master:M` still takes the master route, since it receives from M as well as sending into N, and a master route that finds no candidate is `NO_SHARED_PEER` rather than a fall back to in place. Refusals from `route` are `NOT_EMULATED` (which also covers a `.` or `..` component, because resolving it would make `appVisible` name a directory the mount is not at), `IS_TREE_ROOT`, `RESERVED_NAME` (under `Android/`, vold's) and `NO_SHARED_PEER`; `localRefusal` is the part of the verdict a path alone decides, for a caller that has no root. The enum carries three more, `NOT_ABSOLUTE`, `IS_FILESYSTEM_ROOT` and `HAS_DOT_COMPONENT`, which this file never answers — they belong to `MountpointPolicy.refusalFor`'s own arms and live here only because that function's return type is this enum. |
| `Fuse.kt` | The slice of the FUSE kernel ABI (`linux/fuse.h`) the bridge speaks: opcode numbers, struct sizes and field offsets as constants against a frozen ABI (including `CREATE_OUT_SIZE`, the one sum a CREATE reply must hit exactly or every open fails EIO), the FATTR_* SETATTR mask, errno values, `align8`, the `reply` header writer (errno passed positive, stored negated, refusals never carrying a payload) and `refusal`, which is now `READLINK -> EINVAL, else ENOSYS`: on a mount that accepts writes EROFS would be a false claim about the filesystem, and for RENAME2, FALLOCATE and the xattr setters ENOSYS is additionally what the kernel caches to stop asking. |
| `FuseDevice.kt` | The mounted `/dev/fuse` connection as two unbuffered streams over one descriptor. Deliberately not closeable: the descriptor's owner is whoever adopted it. One syscall per message is mandatory, since FUSE frames requests and replies by syscall boundary. |
| `FuseNodes.kt` | `NodeTable` — the nodeid <-> path map, the only place a path exists once mounted, with allocation (`intern`) separated from kernel referencing (`lookedUp`/`countLookup`/`forget`) so a plain READDIR can reuse nodeids as inode numbers without leaking them, and a removed name separated from a forgotten id: `detach` retires the name into a tombstone (`Node.path` becomes null) while the id lives on for the kernel's pending FORGET, so a re-created name gets a fresh nodeid instead of resolving to the dead one. Eviction only unbinds a name that still points at that id, which is the same bug from the other side. `path` is a var so a later subtree re-key is possible; the root is never retired. `DirRow` + `Dirents.pack` build `fuse_dirent`/`fuse_direntplus` pages: 8-byte-aligned records, cookies one past each row, zeroed padding, and the entry prefix on every record in READDIRPLUS mode. |
| `FuseNfsDaemon.kt` | The opcode loop, reads and writes. Negotiates FUSE_INIT (512 KiB reads and writes via FUSE_MAX_PAGES, READDIRPLUS, 5 s attr/entry TTL, and deliberately NOT FUSE_WRITEBACK_CACHE), serves LOOKUP/GETATTR/SETATTR/OPENDIR/READDIR/READDIRPLUS/RELEASEDIR/OPEN/READ/WRITE/RELEASE/CREATE/MKDIR/UNLINK/RMDIR/STATFS/ACCESS/FORGET/BATCH_FORGET/FLUSH/FSYNC/FSYNCDIR/DESTROY out of an `NfsSession`, refuses the rest per `Fuse.refusal`. READ refills short server replies, because a short FUSE reply means end of file and would zero-fill the caller's page; WRITE loops for the same reason in reverse. Write-through: a failure is reported by the WRITE that caused it, which is where `write(2)` sees it, so FLUSH — whose status is `close(2)`'s — has nothing left to report and RELEASE, whose status the VFS discards, is not asked to. `errnoFor` maps the seam's sealed `NfsFailure` onto errnos. Handles carry their access mode, so a WRITE against a read-only open is EBADF. Several workers read the device concurrently. |
| `FuseDaemon.kt` | Entry point `app.mammon.FuseDaemonKt.main(<fd> <host> <port> <export> [uid:gid:aux])`, started by `RootMount`'s root shell under `app_process`. The identity field is optional so the already-released module's four-argument boot automount keeps working; absent, the daemon claims `AuthIdentity.DEFAULT` and says so in the line it logs. Its own `UID`/`GID` constants stay 0 — those are what the local kernel is told owns the files, not the AUTH_SYS identity. No Android context exists here. Checks that `/proc/self/fd/<fd>` really is `/dev/fuse` before adopting it with `ParcelFileDescriptor.adoptFd`, then serves until FUSE_DESTROY. Kept from R8 by an explicit rule in `app/proguard-rules.pro`, since nothing in the dex references it. |

which is every file under `app/src/test/kotlin/app/mammon/`:

`TransportLossTest`, `Nfs3MappingTest` (the v3 status table against the v4.1 one, so the
same condition refuses identically on both backends), `Nfs3FragmentBoundTest` (the v3
reply bound against the 65532-byte fragment threshold it was chosen for),
`Nfs3HandleCacheTest` (the handle cache's 5 s bound off an injected clock, and the
re-resolve that restarts it).
`EmulatedMountTest` reaches past its own name:
besides the routing rule it drives `RootMount.mounted` with an injected teardown, which
is the only way a JVM test can pin the propagation verdict at all — a real teardown
spawns `su`.

`FslibAutomountFuseFdTest` is the odd one out: it actually runs `magisk-module/fslib.sh`
under mksh, so it pins the shell half against the Kotlin half — the fd-3 group
redirection surviving `exec`, the `--nice-name` position, and the whole routing rule.
That last part is why the file exists in its current shape: the `Android/` and
non-emulated refusals reached before anything is mounted, a subdirectory of emulated
storage routed to the shared master, the `.`/`..` traversal a hand-edited pref can
carry into a root `mkdir -p`, an in-place route on a view that is its own master, the
octal-escaped mount point, first-wins among peers, `propagate_from:` ahead of `master:`,
the digit-shaped `<u>` a shell glob would not have enforced under `/mnt/user`, and the
reduction of the saved spelling to one spelling — `normalize`'s three operations in its
order, the trim table character for character against `Char.isWhitespace`, and the fact
that routing is handed the SAVED string, since one pass and two do not agree.
Each of those is one rule written twice, in Kotlin and in POSIX `sh`, and
the shell copy is the one no compiler checks. Every case that needs the
shell is `assumeTrue`-gated on mksh being on PATH, so on a host without it they SKIP:
a green run is not evidence about the shell until the skips are checked.
`MountpointVerbatimTargetTest` drives the same script through a smaller harness of its
own for the one rule that file does not reach: the mountpoint the app hands to root
VERBATIM. It proves the module refuses the same not-absolute-as-saved spellings the
app now does, mounts the same absolute ones at the same byte, and records the CLASS the
two differ on: a value `mammon_pref_value`'s line-anchored `sed` cannot read at all —
an empty `<string>` and any value carrying a newline alike — takes the module's own
`/mnt/nas` fallback as if the key were absent, while SharedPreferences hands the app the
value itself and it answers that. Two rows, not one, and naming either as the only one
is what a later reader would judge a NEW divergence against.

No services or receivers exist yet. The FUSE daemon is not a service: it is a separate
root process under `app_process`, outliving the `su` call that started it and ending
when `umount` makes the kernel send FUSE_DESTROY.

- `application`: `allowBackup=false`, theme `Theme.Mammon`.
- One exported activity `MainActivity` with the `MAIN`/`LAUNCHER` intent filter and

- One exported DocumentsProvider `app.mammon.nfs` (`NfsDocumentsProvider`) guarded by
  `android:permission="android.permission.MANAGE_DOCUMENTS"` (the AOSP contract —
  `DocumentsProvider.attachInfo` refuses unprotected authorities), `grantUriPermissions=true`,
  `DOCUMENTS_PROVIDER` intent filter; SAF clients reach it through DocumentsUI, which holds
  that signature permission. Becoming writable needs no declaration of its own: writes are
  gated per URI by the grant the system issues, and `android:permission` already covers
  reads and writes. `android:writePermission` would be worse than redundant — it takes
  precedence over `android:permission`, so a weaker value there would widen write access
  past the read gate rather than tighten anything.

## Planned — future, nothing exists yet

All three directions in `docs/guides/architecture.md` are built; what remains open:

- **Mount service** — foreground service owning a mount session (easysshfs-style);
  today `RootMount` runs one-shot from the activity, and the FUSE daemon it starts
  survives on its own rather than under a service lifecycle.
- **Boot receiver** — restore configured mounts after `BOOT_COMPLETED`.
- **Rename** — not in the `NfsSession` seam, so neither front end offers it. FUSE
  answers RENAME with ENOSYS and SAF withholds `FLAG_SUPPORTS_RENAME`. Adding it means
  a backend RENAME operation first; everything else the seam exposes is now consumed.
